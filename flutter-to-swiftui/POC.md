# Flutter → SwiftUI POC 制作方案

> **定位**：本文件是 [方案 V4](00-方案V4-暂定最终版.md) 的**前置验证**，不替代 V4。
> V4 的 P0–P7 是 POC 通过后的全量迁移路径；POC 只取其中的最小链路，**目标是用最小成本证明一件事**：
> **用 AI 手段能把 Flutter 页面快速转成 SwiftUI，并且真的用上公司内部组件库。**

---

## 1. 要证明什么：四个命题

POC 的结论只有"成立"或"不成立"两种。四个命题**必须同时成立**才算通过，任何一个不成立都不能对外说"AI 可行"。

| # | 命题 | 一句话判据 | POC 不成立时看起来像什么 |
|---|---|---|---|
| **P1** | **快** | 单屏耗时显著低于人工重写 | 比人写还慢，或省下的时间全花在修 AI 产物上 |
| **P2** | **对** | 状态机与边界全覆盖，Parity Checklist 全绿 | 只跑通 happy path，空态/错误态/分页没做 |
| **P3** | **用库** | 页面主体由内部组件库构成 | 满屏裸 `SwiftUI` 或自绘，组件库只贴了个按钮 |
| **P4** | **可持续** | 改一次 Figma 稿重生成，手写逻辑零丢失 | 一改稿就要人重新接逻辑，说明产线不可复用 |

> P3 是最容易被自欺欺人的一条：**"能调通组件库"不等于"页面是用组件库搭的"**。必须用复用率量化。
> P4 是最容易被跳过的一条：它恰恰是整条方案的核心假设（V4 §3 可再生层 vs 持久层），POC 不验它，等于没验。

## 2. 范围

### 2.1 做什么（In Scope）

| 项 | 说明 |
|---|---|
| 样本屏 | **1 个中等复杂屏**：列表 + 进入详情，含 loading / empty / error / 分页 |
| 链路 | Dart → Screen Spec → Layout（GenUI）+ Feature（AI）→ 真机运行 |
| 组件库 | 只接 **3–5 个高频组件**，其余暂时转发系统组件 |
| 验证 | Parity Checklist + 改稿重生成实验 |

### 2.2 不做什么（Out of Scope，明确排除）

| 不做 | 属于 V4 哪个阶段 |
|---|---|
| 数据迁移（导出/转换/埋点上报） | §5.7 / P3 |
| 灰度、Kill switch、回滚、双端兼容 | §5.8 / §5.9 / P6 |
| 埋点全量对齐与 CI 断言 | §5.6 |
| 组件库治理（缺口语义、版本策略、SLA、snapshot 全量回归） | §5.1 / C1–C8 |
| GoldenExamples 语料库（20–30 个 Feature） | §4.6 / D1–D5 |
| 资源与本地化迁移、Universal Link、隐私清单、性能门禁 | 全量迁移事项 |
| 表单屏、自绘屏、复杂动画 | 留给 P4 试点，POC 不碰 |

> **纪律**：POC 期间任何"顺手把迁移也做了"的想法都要拒绝。POC 的目的是**缩短证伪周期**，不是提前交付。

## 3. 前置条件（缺一即阻塞，先确认再动手）

| # | 条件 | 怎么确认 | 阻塞后果 |
|---|---|---|---|
| **A**⭐ | 组件库 iOS 部署 target | 拿 Podfile/SPM 清单，看最低 iOS 版本是否 ≤ 16 | 与基线冲突则方案需推翻（V4 §10 #1） |
| **B**⭐ | GenUI 当前可用性 | 拿 1 个 Figma Frame 实跑一次，看能否出可编译代码 | 不可用则 POC 降级为"Figma → Agent 直出"，**结论不能外推到 GenUI 产线** |
| **C** | 样本屏可获取 | Flutter 源码 + Figma Frame + 抓包环境 + 真机 | 缺则 Analyzer 无法产出可靠 Spec |
| **D** | 人工基线数据 | 指定 1 名工程师手写同屏，记录实际工时 | 没有基线，"快"无法量化 |

**B 是最容易含糊的一项。** 如果 GenUI 还没就绪，直接说明"本轮 POC 验证的是 AI 直出能力，不含 GenUI 再生环节"，并把 P4 命题标记为"未验证"，不要混在一起报结论。

## 4. 七步制作流程

每步都有明确产出物，**上一步产出不全，不进下一步**。

### Step 0 — 选屏与建基线（0.5 天）

- 选屏标准：有列表、有分页、有 4 种以上状态；**不要挑最简单的屏**，也不要挑自绘/动画屏。
- 让 1 名不参与本项目的工程师按 Figma 手写同一屏，记录：**工时、代码行数、返工次数**。这是 P1 的对照值。
- 产出：`poc/00-scope.md`（屏名、Figma Frame、Dart 入口文件、人工基线数据）。

### Step 1 — 组件地图（0.5 天）

```bash
python3 tools/scan_flutter_widgets.py --path <Flutter工程路径> --out ./poc/scan
```

- 看三样东西：`widget_inventory.md` 的自定义组件清单、UI 基线判断（Material/Cupertino/自绘）、风险打标（`CustomPainter`/`BackdropFilter`/Platform Channel）。
- **决策点**：风险打标里若出现大量自绘/Shader，换屏。POC 不该消耗在最难的路径上。
- 产出：`poc/01-component-map.md`（组件清单 + 选定的 3–5 个待接组件）。

### Step 2 — Screen Spec（1 天）

- Analyzer Agent 只读 Dart + 抓包 + 录屏，按 [`templates/screen_spec.md`](templates/screen_spec.md) 填 14 节。
- **两个必查项**（V4 §4.3 已标注为最高频遗漏）：
  - 第 2 节「状态机」：把 Flutter 里隐含的 `isLoading` + 判空**摊开成穷举枚举**；
  - 第 9 节「并发」：请求取消、后发先至、重复提交、Token 刷新合并。
- 抓包优先级高于读代码（V4 §4.2）：代码写的是开发者以为的契约。
- 产出：`poc/02-screen-spec.md`，**由人 review 一遍**再放行。

> Spec 是后续所有环节的唯一输入。这里偷懒，后面 Agent 必然产出"Dart 味的 Swift"，而且返工成本翻倍。

### Step 3 — 适配层最小集（1 天）

只做 POC 需要的 3–5 个组件，全部遵循"业务页不裸调库组件"：

```swift
// 全 POC 唯一依赖 DS 的地方
struct AppButton: View {
    let title: String
    let isLoading: Bool
    let action: () -> Void

    var body: some View {
        DSButton(title: title, isBusy: isLoading, action: action)
    }
}
```

- 若某组件库缺（三态清单里的"库缺"），**不要 fork**（V4 §5.1 硬规则），先用系统组件转发并记入缺口清单。
- 每个组件配 `#Preview` 四态（默认/加载/空/错误），这同时是 P4 改稿实验的对照基准。
- 产出：`poc/03-adapters/`（组件薄壳 + 缺口清单）。

### Step 4 — GenUI 出 Layout（1 天）

- 输入：Figma Frame。输出：`XxxLayout.swift` —— **纯渲染、零 `@State`、零业务判断**。
- 检查三条硬规则：无 `#hex` 字面量、无硬编码 frame 尺寸、可点击元素有 `accessibilityLabel`（V4 §11 卫生门禁的子集）。
- 产出：`poc/04-layout/XxxLayout.swift`。

### Step 5 — Feature 层（1.5 天）

- Feature Builder **只读 Spec，禁止读 Dart**（V4 §4.1 Spec 墙）。
- 按 V4 §3.2 分文件，其中 **❌ 类文件（DomainState / DomainAction / Logic / Feature）永不由 GenUI 覆盖**：

```text
XxxLayout.swift          ← GenUI，可随时覆盖
XxxViewState.swift       ← GenUI，可随时覆盖
XxxViewAction.swift      ← GenUI，可随时覆盖
XxxDomainState.swift     ← 手写
XxxDomainAction.swift    ← 手写
XxxLogic.swift           ← 手写（reducer / Effect / 依赖）
XxxFeature.swift         ← 手写
```

- POC 阶段判定：**有状态机或多步流程用 TCA；纯展示+单请求可用 `ObservableObject`**（V4 §5.4）。若用 TCA，iOS 16 需 Perception 回移植，**在这里实测样板量**并记录（这是 V4 待验证项）。
- 产出：`poc/05-feature/`。

### Step 6 — 真机验收（1 天）

逐项过 Spec 第 14 节的 Parity Checklist：

- [ ] 状态机全覆盖（loading / empty / error / offline / loadingMore…）
- [ ] 边界全覆盖（超长文本、图片失败、快速连点、退出时请求未完成）
- [ ] 无硬编码色值/间距
- [ ] VoiceOver + Dynamic Type 可用
- [ ] 视觉与 Figma 关键页对照通过
- [ ] 请求取消与竞态实测（进页面 → 立即退出 → 无崩溃、无错数据）

**同时记录人工介入量**：为让 POC 跑通，人改了多少行 AI 产物、改了什么类型（编译错 / 逻辑错 / 视觉错）。

### Step 7 — 改稿重生成实验（1 天）⭐ 核心命题

这是 POC 与"随便做个 demo"的分水岭。

1. 在 Figma 上改一处**结构性变更**（例如按钮从底部固定改为列表内嵌、或增加一个状态区块）；
2. 重新跑 GenUI 出 `XxxLayout.swift` / `XxxViewState.swift` / `XxxViewAction.swift`；
3. **手写层一行不动**，执行编译；
4. 记录：编译是否通过？报错是否指向手写层？按报错修了哪些地方？业务逻辑是否零丢失？

- 通过：说明 V4 §3 的文件所有权隔离真的成立。
- 不通过：**POC 不成立**，且这是最有价值的结论 —— 比跑通十个页面都值钱。
- 产出：`poc/07-regen-report.md`（改稿前后的 diff + 编译结果 + 结论）。

## 5. 度量表（POC 结论就看这张表）

| 指标 | 怎么量 | 目标（建议阈值） | 对应命题 |
|---|---|---|---|
| 单屏总耗时 | Step 1–6 的 wall-clock 合计 | ≤ 人工基线的 **40%** | P1 |
| 人工基线 | Step 0 实测工时 | 对照值 | P1 |
| 首版编译通过率 | 首版即编译通过且 Parity 通过 | ≥ **60%** | P2 |
| 返工轮次 | 达到验收的平均迭代次数 | ≤ **3** | P2 |
| Parity 通过率 | 通过项 / Checklist 总数 | **100%**（关键路径不允许豁免） | P2 |
| **组件库复用率** | DS 组件数 / 页面 UI 元素总数 | ≥ **70%** | P3 |
| **改稿逻辑保留** | 重生成后手写层零修改即编译通过 | **必须 100%** | P4 |
| 人工介入量 | 人改动行数 / AI 产出总行数 | ≤ **10%** | P1/P2 |

> 组件库复用率的统计口径要提前定死（按"顶层可见元素"计，不按代码行计），否则事后容易各自解释。

## 6. 失败判据（提前写死，避免事后找补）

满足**任意一条**即判定 POC 不成立，如实上报，不调整口径重算：

1. 单屏总耗时 ≥ 人工基线（"快"不成立）；
2. 组件库复用率 < 50%（"用库"不成立，实际是裸 SwiftUI）；
3. 改稿重生成后，手写层需要人工重写才能编译（"可持续"不成立）；
4. 关键路径存在无法通过 Parity 的状态或边界，且根因在 AI 产物（"对"不成立）。

**POC 不成立 ≠ 项目失败**。它证明的是"当前配置下这条路走不通"，通常指向具体原因：GenUI 覆盖不足、组件库语义不匹配、Spec 粒度不够。这些正是该在全量迁移前知道的。

## 7. 交付物清单

| 交付物 | 用途 |
|---|---|
| 可运行的真机 Demo（含状态切换演示） | 最直观的证明 |
| 第 5 节度量表（含人工基线对照） | 唯一的量化结论 |
| 改稿前后代码 diff + 编译记录 | 证明 P4 命题 |
| 5 分钟录屏（操作 + 状态切换 + 改稿重生成） | 评审会材料 |
| 缺口与阻碍清单 | 决定是否进入 V4 P0 |
| 结论页：四个命题逐项"成立 / 不成立 / 未验证" | 决策依据 |

> 结论页里出现"未验证"是可以的（例如 GenUI 未就绪导致 P4 无法验证），但不能把"未验证"写成"成立"。

## 8. 时间安排（10 个工作日）

| 天 | 内容 | 出口 |
|---|---|---|
| D1 | 前置条件 A–D 确认 + 选屏 | 无阻塞项 |
| D2 | 组件地图扫描 + Spec 起稿 | 风险打标无致命项 |
| D3 | Spec 完成 + 人工 review | Spec 14 节无空项 |
| D4 | 适配层最小集 | 3–5 个组件四态预览可用 |
| D5 | GenUI 出 Layout | 卫生门禁三项通过 |
| D6–D7 | Feature 层（Domain/Logic） | 编译通过 |
| D8 | 真机验收 + Parity | 关键路径全绿 |
| D9 | 改稿重生成实验 | 有明确结论 |
| D10 | 度量汇总 + 录屏 + 结论页 | 可评审 |

若 D5 卡在 GenUI 不可用，立即降级为 Agent 直出，并在结论页把 P4 标为"未验证"，不要延期硬等。

## 9. 风险与应对

| 风险 | 应对 |
|---|---|
| 组件库 iOS target 高于 16 | 立刻上报，这是推翻选型的唯一信息；POC 暂停，不做降级妥协 |
| GenUI 产出质量差（绝对定位、硬编码色值） | 先修 Figma（Auto Layout / Variables），而不是在代码里补；Figma 质量决定 GenUI 质量 |
| Agent 写出"Dart 味的 Swift" | 说明 Spec 墙破了：检查 Implementer 是否真的只读 Spec；必要时在 prompt 里加反例 |
| 选屏里藏了自绘组件 | Step 1 就该发现并换屏，不要硬啃（自绘属于 P4 的 K3 试点） |
| POC 期间被拉去做全量迁移事项 | 回到第 2.2 节范围表，明确拒绝 |

## 一句话总结

POC 要交付的不是"一个能跑的页面"，而是**四个命题的量化结论**。
页面只是载体；**改稿重生成后逻辑不丢**那一项，才是这条产线能不能规模化的答案。
